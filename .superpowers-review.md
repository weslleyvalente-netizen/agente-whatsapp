## HIGH

### H1. A device stays bound to the previous seller after logout or user switch, so seller B gets seller A's leads (CONFIRMED code path)
- Files: `apps/web/src/components/layout/user-nav.tsx:23` (logout only calls `supabase.auth.signOut()`); `apps/web/src/components/settings/push-notifications-card.tsx:36-46` ("active" comes only from `pushManager.getSubscription()` in the browser, with no server check).
- What goes wrong: Márcio turns on push on a shared store tablet or phone, then logs out. Another seller logs in on the same browser. The server row `push_subscriptions(endpoint -> user_id=Márcio)` is still there, so the device keeps showing Márcio's "Novo lead: {nome}" and customer message snippets on the lock screen. The card shows "Ativas" to the second seller, so they think the alerts are their own. This breaks seller isolation. The same mismatch happens after a 404/410 cleanup: the server row is gone, but the browser still says "active", so the user gets no pushes and nothing tells them.
- Fix: (a) on logout, before `signOut`, get the registration, POST `/push/unsubscribe` with the endpoint, then call `subscription.unsubscribe()` (best effort, inside try/catch). (b) In `refresh()`, when a browser subscription exists, re-POST `/push/subscribe` so the server row is (re)bound to the current user. Or add `GET /push/status?endpoint=` that returns whether the endpoint belongs to `request.user.id`, and show "inactive" if it does not.

### H2. Recipients are never re-checked against current org membership or active seller status, so an ex-seller keeps getting customer data (PLAUSIBLE)
- Files: `packages/database/src/push/send.ts:25` (selects subscriptions by `user_id` only and ignores `organization_id`); `packages/database/src/queries/push.ts:57,77` (recipient = `sales_reps.user_id`); `packages/database/src/queries/push.ts:122` (recipient = `conversations.assigned_to`).
- What goes wrong: a seller is removed from `organization_members`, or their `sales_reps` row is deactivated, but the auth user still exists. `conversations.assigned_to` only becomes NULL when the auth user is deleted, and `push_subscriptions` only cascades on auth user or org deletion. The ex-seller's phone keeps getting customer names and message text for every conversation still assigned to them. A user in two orgs also gets pushes from both orgs on every device, whatever org they subscribed under.
- Fix: in `runPushSweep`, before sending, check that `c.userId` is a current `organization_members` row of `c.organizationId` (cache per sweep), and for assignment triggers that the rep is active. In `sendPushToUser`, take `organizationId` and filter `.eq("organization_id", orgId)`. Also delete a user's `push_subscriptions` for an org when their membership is removed (trigger on `organization_members` DELETE).

## MEDIUM

### M1. The messages sweep scans the whole `messages` table every 30 s, even when the flag is off for every org (PLAUSIBLE)
- Files: `packages/database/src/queries/push.ts:99-101`; `apps/worker/src/workers/push-notifications.ts:23-34`.
- What goes wrong: once VAPID keys are set (they are needed for the test button), the worker runs all three queries every 30 s whatever the flag says. The flag is only checked per candidate afterwards. The messages query has no `organization_id` filter. The only matching index is `(organization_id, role, created_at)` and the org column leads it, so Postgres falls back to a seq scan or a poor plan joined with `conversations!inner`. That load runs around the clock even with the feature "off". Turning the flag off does not make the feature inert as the spec says.
- Fix: at the start of the sweep, load the org ids with `settings->>'push_notifications_enabled' = 'true'` and return early if there are none. Pass `orgIds` into every list function and add `.in("organization_id", orgIds)`. That uses the existing `idx_messages_org_role_created_at` index.

### M2. The SLA-risk push fires in the same sweep as "Novo lead" (CONFIRMED)
- Files: `apps/worker/src/workers/push-notifications.ts:14` (`SLA_WINDOW_MINUTES = 15`); `packages/database/src/queries/push.ts:68-72`; default SLA is 15 min (`settings/page.tsx:100`, `DEFAULT_LEAD_SLA_MINUTES`).
- What goes wrong: a new assignment has `sla_due_at = now + 15 min`, so `listSlaRiskCandidates` picks it up in the very first sweep. The seller gets "Novo lead: Ana" and "Responda Ana — faltam 15 min" together. If the customer also messaged, a third push for the same lead arrives too. Each has a different tag (`assign-`, `sla-`, conversation id), so none replaces another.
- Fix: make the SLA window a fraction of the SLA (for example `min(5, sla/3)` minutes), or only consider assignments with `created_at <= now - 2 min`. Use one shared tag per lead, such as `lead-{conversation_id}`, for all three triggers so a later push replaces the earlier one. Add a test where one assignment is both new and inside the SLA window.

### M3. No cap per user or per sweep, and limit truncation loses events for good (CONFIRMED)
- Files: `packages/database/src/queries/push.ts:53` (`limit(200)`), `:101` (`limit(500)`), `:72`; `apps/worker/src/workers/push-notifications.ts:49`.
- What goes wrong: (a) a `bulk_reassignment` of 150 leads to one seller sends 150 separate pushes (distinct tags) in one sweep. That is a notification storm, and the push service may throttle it. (b) If more than 500 customer messages arrive inside one window, only the oldest 500 are read (ascending order). The cursor then jumps to `now - 10s`, so the rest are never notified.
- Fix: group candidates per user in each sweep. Send up to N (for example 5) individually, then one summary push ("+12 novos leads") with a fixed tag. Advance the cursor only to the `created_at` of the last row read when the limit was hit (keyset cursor) instead of to `now`.

### M4. The cursor advances even when a trigger query failed, so that window's events are lost (CONFIRMED)
- File: `apps/worker/src/workers/push-notifications.ts:34` (`catch ... continue`) and `:49` (the cursor always moves).
- What goes wrong: a transient Supabase error on the assignments or messages query skips that source, and `cursor.since` still moves to `now - 10s`. Those leads and messages are never notified. SLA is not affected because it has no cursor.
- Fix: keep a separate cursor per source and only advance a source's cursor when its load succeeded. Or leave `cursor.since` unchanged when any cursor-based source failed.

### M5. The "never had a human reply" check can be truncated, causing pushes for conversations that were already answered (PLAUSIBLE)
- File: `packages/database/src/queries/push.ts:112`.
- What goes wrong: `select conversation_id from messages where role='human_agent' and conversation_id in (...)` returns every human message, with no limit and no distinct. PostgREST `max_rows` (Supabase default 1000) truncates it. With long human chats, some answered conversations are missing from `answered`, so the seller gets pushes for AI-handled conversations they had already answered. It is also wasteful.
- Fix: use an RPC with `EXISTS` per conversation, or `lead_assignments.first_human_message_at` / a `conversations` column if one exists. At least add `.limit(needCheck.length * K)` and dedupe, but the RPC is the correct fix.

### M6. On iOS, `Notification.requestPermission()` is called after several awaits, so the user gesture may be gone (PLAUSIBLE)
- File: `apps/web/src/components/settings/push-notifications-card.tsx:57-61`.
- What goes wrong: `enable()` awaits `apiFetch('/push/public-key')`, `serviceWorker.register`, and `serviceWorker.ready` before it asks for permission. WebKit needs a user gesture for the permission prompt. After the network round trip and SW install the transient activation can expire, and the prompt is then rejected or never shown on iPhone, which is the main target device.
- Fix: call `Notification.requestPermission()` first, synchronously inside the click handler, and only then fetch the key, register and subscribe. Test it on a real iPhone (iOS 16.4+) in standalone mode.

### M7. `push_notification_log` grows without limit (CONFIRMED)
- File: `supabase/migrations/20261018120000_push_notifications.sql:24-30`.
- What goes wrong: there is one row per lead, per SLA alert and per customer message, forever. The message keys are the big source: every customer message in an owned conversation adds a row. The table and its PK index grow without limit, and nothing ever reads rows older than the 2 min lookback plus the SLA window.
- Fix: delete old rows in the worker, for example `delete from push_notification_log where created_at < now() - interval '7 days'` once an hour (use the existing `created_at` index, or a repeatable BullMQ job like customer-audio-retention). Or add a `pg_cron` job in the migration. Document it in the runbook.

## LOW

### L1. Subscription hijack via upsert on `endpoint` (PLAUSIBLE, low impact)
- Files: `packages/database/src/queries/push.ts:18-21`; `apps/api/src/routes/push/index.ts:25`.
- What goes wrong: the API uses the service role, so RLS does not apply. An authenticated user A who learns user B's endpoint URL (it is unguessable, but could show up in support screenshots or logs) can POST it with their own keys. The row's `user_id` and keys are overwritten. B stops getting pushes (denial of service), and A's payloads go to B's device encrypted with keys B cannot decrypt.
- Fix: before the upsert, if a row exists for this endpoint with a different `user_id`, only reassign it when the submitted `p256dh` and `auth` match the stored ones (proof that the caller has that browser subscription). Otherwise return 409. A real device handover still works because the same browser sends the same keys.

### L2. The dedupe key is claimed before sending, so delivery is at-most-once (CONFIRMED)
- File: `apps/worker/src/workers/push-notifications.ts:39-42`.
- What goes wrong: the keys are claimed, then `sendPushToUser` throws (for example the subscriptions select fails). The key stays claimed and the notification is never retried. Retryable push service errors (429/5xx) are also only counted as `failed`.
- Fix: in the catch, delete the claimed keys, or claim after the send when `sent > 0 || no subscriptions`. At-most-once is acceptable if you write it down as a deliberate choice.

### L3. The phone number appears on the lock screen when the contact has no name (CONFIRMED)
- File: `packages/database/src/queries/push.ts:41` (`contactLabel` falls back to `phone`).
- What goes wrong: the spec says no sensitive data beyond name and a short snippet. A full customer phone number shows on the lock screen and in the push service payload.
- Fix: fall back to "Cliente" or a masked number (`•••• 1234`).

### L4. Migration robustness and RLS details (CONFIRMED)
- File: `supabase/migrations/20261018120000_push_notifications.sql:3,18-21,24`.
- `CREATE TABLE` / `CREATE INDEX` / `CREATE POLICY` are not idempotent: re-running after a partial apply fails. Use `IF NOT EXISTS` and `DROP POLICY IF EXISTS` before each `CREATE POLICY`. It is additive only, so no breaking change.
- The INSERT/UPDATE policies let a user write a row with any `organization_id`. Add `AND organization_id IN (SELECT get_user_org_ids())`.
- Use `(select auth.uid())` instead of `auth.uid()`, matching the existing seller-isolation policies (initplan perf).
- `push_notification_log` has RLS on and no policies, so only the service role can use it. Good. Also add `REVOKE ALL ON public.push_notification_log FROM anon, authenticated;` as defense in depth.

### L5. `notificationclick` can fail on a window the service worker does not control (PLAUSIBLE)
- File: `apps/web/public/sw.js:24-28`.
- What goes wrong: `matchAll({ includeUncontrolled: true })` can return a window this service worker does not control (opened before it activated). `WindowClient.navigate()` rejects for uncontrolled clients, so the click focuses the app but does not open the conversation.
- Fix: `focused.navigate(url).catch(() => self.clients.openWindow(url))`, or prefer controlled clients first.

### L6. Test quality (CONFIRMED)
- `apps/worker/src/workers/push-notifications.test.ts:65-69` ("cada vendedor recebe só o que é dele") is tautological. It only checks that the worker passes through the `userId` the mock returned, and proves nothing about isolation.
- `packages/database/src/queries/push.test.ts:47-59` checks none of the security- and correctness-relevant filters (`status='pending'`, `rep_id not null`, `gte created_at`, `role='contact'`, `conversations.assigned_to not null`). Removing any of them would not fail a test. The Proxy builder also accepts any PostgREST syntax, so embed/filter syntax is never validated. A pglite test exists in this package's devDeps and could be used.
- There is no test for the settings card component (the spec asks for a status component test). Only the pure `getPushStatus` is tested.
- Missing tests: cursor behaviour when a source fails, a new lead and SLA risk in the same sweep, the per-user cap, and an assigned_to user who is no longer a member.
