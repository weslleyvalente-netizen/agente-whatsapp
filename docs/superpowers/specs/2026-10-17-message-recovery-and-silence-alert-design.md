# Recuperação de mensagens perdidas e alerta de silêncio

Aprovado pelo usuário em chat (2026-10-17). Incidente: o Redis parou às ~23h13 de 16/10 e voltou às 8h45 de 17/10; durante esse tempo a Evolution não entregou as mensagens de clientes ao CRM (a API estava no ar, mas a fila não), então nenhum cliente foi respondido nem chegou aos vendedores, e ninguém percebeu por ~9 h. Duas entregas: (A) ferramenta de recuperação das mensagens que a Evolution guarda e o CRM não recebeu; (B) detecção e alerta de "silêncio".

## A) Recuperar mensagens perdidas (apps/api)
**Rota** `POST /organizations/:organizationId/admin/recover-messages` (somente owner/admin da organização; 403 caso contrário). Corpo (zod): `{ since: string ISO (obrigatório), until?: string ISO, dryRun?: boolean (padrão true) }`. Máximo de janela: 7 dias. Resposta: `{ dryRun, instance, fetched, alreadyInCrm, toRecover, customers, replayed, failed, skipped:{groups,nonContent}, sample:[{phoneLast4, firstAt, lastAt, count}] }` (sem texto de mensagem nem telefone completo na resposta).
**Como funciona:**
1. Busca na Evolution (API já configurada no servidor: reutilize o cliente/serviço Evolution existente do projeto; endpoint `POST /chat/findMessages/{instanceName}` com `where: { key: { fromMe: false }, messageTimestamp: { gte: <epoch>, lte: <epoch> } }`, paginando até esgotar; leia como as outras partes do código chamam a Evolution — URL interna e chave via env, nunca em log).
2. Descarta grupos (`@g.us`), tipos sem conteúdo (use a mesma função `isNonContentMessageType` do webhook) e mensagens cujo `evolution_message_id` já existe em `messages` (mesma checagem `messageExistsByEvolutionId` usada no webhook).
3. Com `dryRun=false`: reenvia cada mensagem restante, **em ordem cronológica**, pelo MESMO caminho do webhook, usando `app.inject({ method: "POST", url: "/webhooks/evolution", headers: { apikey: process.env.WEBHOOK_SECRET }, payload })` com o payload no formato que a Evolution envia (`event: "messages.upsert"`, `instance`, `data: { key, pushName, message, messageType, messageTimestamp, ... }` — monte a partir do registro do findMessages e valide contra `evolutionWebhookPayloadSchema`). Assim o fluxo normal faz tudo: grava, cria contato/conversa/negócio, enfileira a IA (que responde) ou segue o encaminhamento ao humano. Intervalo de ~1,5 s entre mensagens do mesmo lote e processamento sequencial para não sobrecarregar; ao final devolve o resumo. Uma falha de uma mensagem não interrompe as outras (conte em `failed`).
4. Idempotente: rodar duas vezes não duplica (dedupe pelo id).
**Atenção ao timestamp:** a mensagem recuperada deve manter o horário ORIGINAL (`messageTimestamp`) em `created_at`; confirme como o webhook define `created_at` e, se usar "agora", ajuste (parâmetro opcional/flag interna) para respeitar o original sem quebrar o fluxo normal. A IA responderá agora (atrasada) — é o desejado pelo usuário.
**Interface (apps/web, Configurações):** cartão "Recuperar mensagens perdidas" visível só para owner/admin: campos de data/hora inicial e final (padrão: últimas 24 h), botão "Verificar" (dryRun) que mostra "X mensagens de Y clientes não chegaram ao CRM" e botão "Recuperar agora" com confirmação explícita ("a IA vai responder esses clientes agora").
Testes: vitest da rota (permissão, janela >7 dias → 400, dryRun não envia nada, dedupe, ordem cronológica, falha isolada, sem vazamento de telefone completo/segredos) com a Evolution e o `inject` simulados.

## B) Alerta de silêncio (apps/api + apps/web)
**Independente do Redis** (se o Redis cair, o worker também cai): roda num `setInterval` no processo da API (ou onde já houver rotina periódica sem fila), a cada 5 min, e guarda o estado em memória.
Condições de alerta (apenas em horário comercial da organização, `isBusinessOpen` + `resolveBusinessCalendar`):
1. **Silêncio**: nenhuma mensagem de cliente (`role='contact'`) nova nas últimas 2 h enquanto, nos 7 dias anteriores, a média de mensagens de cliente na mesma faixa de horário seria > 0 (evita alarme falso em dia morto; use contagem simples por faixa);
2. **Redis**: `ping` na conexão Redis (use o helper existente de `packages/queue`) falha ou excede 3 s;
3. **Evolution**: instância não `open/connected` (consulte o estado via API da Evolution) — só se a chamada funcionar; falha de consulta conta como alerta.
Ações: (i) guardar um estado `health` consultável: `GET /organizations/:organizationId/health` → `{ status: "ok"|"warning", reasons: string[], lastCustomerMessageAt, redis: "ok"|"down", evolution: "connected"|"disconnected"|"unknown" }` (membros da organização); (ii) o dashboard (apps/web, cabeçalho de `app/(dashboard)/layout.tsx` ou componente próprio) mostra faixa vermelha para owner/admin quando `warning`: "Possível falha: sem mensagens de clientes há X h" com os motivos e link para Configurações → Recuperar mensagens; consultar a cada 60 s; (iii) se `settings.handoff_notification_phone` estiver preenchido, enviar 1 WhatsApp de aviso (texto curto: motivo + hora) pelo mesmo serviço de envio já usado nas notificações de handoff, no máximo 1 aviso a cada 2 h por motivo (anti-spam), e 1 mensagem de "normalizado" ao voltar. Falha ao enviar o aviso não pode derrubar nada.
Testes: função pura de decisão `decideHealth(inputs)` (tabela: horário fechado nunca alerta, silêncio com histórico, Redis down, Evolution caída, anti-spam), rota `/health` e o componente (se houver teste de componente no web; senão tsc/build).
